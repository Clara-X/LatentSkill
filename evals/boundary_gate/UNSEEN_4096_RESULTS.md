# ALFWorld unseen：4096 token 完整任务分析

## 结论

本轮证明 LoRA 既能带来真实任务收益，也会造成大量负迁移；尚未证明
状态门控能够学会这些边界。Always On 的总体提升较小，不能据此宣称稳定优于
Base 或文本技能。尤其对原研究选定的 heat/cool/clean 三项技能，LoRA 的
总体效果为负，应先诊断变换动作执行，再构造门控训练数据。

## 完整性与协议

- 2026-10-22 启动，24 个官方评估子进程全部退出码 0，无失败进程。
- 完整 unseen 集 134 个任务，三组共 402 次评估；每组无重复、无遗漏。
- 8 张 GPU 按任务分片，每个进程直接调用 `evals.alfworld.evaluate`，没有批量
  推理服务、额外 autocast 包装或权重缓存转换。三组使用同一分片集合。
- 环境为 `latentskill`；seed 42；50 步；生成上限 4096；skill/prompt 上限
  均为 4096；保留官方模板、thinking、5 步历史与动作解析。
- checkpoint 为 `checkpoints/latentskill_sft_qwen3_8b/checkpoint-epoch-10`，
  技能目录为 `evals/alfworld/skills`。134 个初始 Base/On prompt 哈希全部一致。

## 完整任务成功率

| 条件 | 成功数 | 成功率 | 相对 Base |
| --- | ---: | ---: | ---: |
| Base | 75/134 | 56.0% | — |
| Always On | 80/134 | 59.7% | +3.7 个百分点 |
| Textual Skill | 83/134 | 61.9% | +6.0 个百分点 |
| Base/On 事后 Oracle | 108/134 | 80.6% | +24.6 个百分点 |
| 三组事后 Oracle | 114/134 | 85.1% | +29.1 个百分点 |

相对 Base，On 有 33 个正迁移、28 个负迁移、73 个同结果任务。同结果包括
47 个都成功和 26 个都失败，并不意味着轨迹或效率相同。净提升为 5 个任务。
Base 的 75 个成功中，有 28 个被 On 破坏（37.3%）；Base 的 59 个失败中，
有 33 个被 On 挽救（55.9%）。文本技能对应 21 个正迁移、13 个负迁移。

Base/On Oracle 相比 Always On 多成功 28 个任务，说明分支之间具有互补性。
但它事后选择整条轨迹，不是已实现的状态门控，也不是动态门控的严格上界。
动态切换会改变后续状态分布，不能直接保证达到 80.6%。

原目标的 heat/cool/clean 子集共有 75 个任务：Base 44/75（58.7%），
On 33/75（44.0%），Text 46/75（61.3%）。On 净下降 14.7 个百分点，
有 13 个正迁移和 24 个负迁移。总体微弱净增益主要由放置任务带动，不能推广到
最初选定的三种变换技能。

仅按本轮结果，关闭 heat/cool、其余类型开启的规则可得 95/134（70.9%）。
这是使用评估标签选规则的事后分析，不能作为验证成绩或部署规则；它提示后续必须
包含“只按技能类型选择”的基线，避免把技能平均质量差异误认为状态边界学习。

## 失败机制：预算、格式与技能执行

| 指标（按步汇总） | Base | On | Text |
| --- | ---: | ---: | ---: |
| 步数 | 4357 | 4203 | 3763 |
| 触及生成上限 | 4.82% | 0.24% | 2.82% |
| 解析失败 | 4.87% | 7.00% | 2.82% |
| 每步平均生成 token | 1259.3 | 432.8 | 1085.8 |
| 总生成 token | 5,486,671 | 1,819,071 | 4,085,788 |

1. **LoRA 缩短输出，但解析质量更差。** On 的总生成 token 比 Base 少约
   66.8%，但这不等价于实测延迟下降。On 有 294 次解析失败，其中 160 次最后
   一行恰好是合法裸动作，却没有满足原解析器的标签要求；这 160 次涉及 60 个
   任务，包括 44 个失败任务。不能把修复格式后可能挽救的任务数直接视为 44。
   修改解析器需要另开对照，不能改写本轮分数。
2. **冷却动作缺失是明确的执行问题。** On 的 17 个冷却失败任务均未执行合法
   `cool ...`，其中 16 个轨迹曾提供该类可用动作。12 个负迁移冷却任务均未执行
   合法 `cool`，其中 11 个没有任何生成截断。抽查 Bread→CounterTop 和
   Tomato→Microwave 轨迹：Base 执行 `cool ... with fridge 1` 后成功；On
   多次把物品放入冰箱再取出，推理中误认为已经冷却，最终耗尽 50 步。
3. **加热也有类似问题。** On 的 14 个加热失败任务中，13 个未执行合法
   `heat ...`，9 个轨迹曾提供该类动作；8 个负迁移任务全部未执行合法加热动作。
   这些计数是观察证据，不足以断言遗漏动作是每个任务唯一的失败原因。
4. **当前更像“技能编译/指令执行退化 + 格式问题”的混合。** 冷却文本明确
   要求先执行冷却动作，但 On 仍可能误用日常物理常识。因此不能把所有失败解释为
   前置条件不成立，也不能让门控承担修复错误技能知识的责任。

## 解释限制与下一步

本轮与前一轮同时改变了 split、任务范围、生成预算和执行后端，不能用两轮差异
单独估计预算的因果效果。当前截断已大幅缓解，但尚未完全消失。

134 个任务仅来自 47 个 task family、4 个 scene；所有 cool/heat 任务都在
scene 10，不能当成 134 个独立场景样本。单次 seed 的净提升也不构成稳定优势证据。
整个 unseen 集中部分状态曾在旧 pilot 中被查看，本轮结果现已用于分析，后续不可
再作为门控训练后未接触过的最终测试集。

建议先在训练/开发数据排查 cool/heat 的变换动作缺失和 On 的格式退化，保持当前
unseen 只作诊断。随后在相同可重放状态分别执行 On/Off，采集剩余任务回报，
区分变换前、变换后、错误位置、未持有所需物品等状态，并按 family/scene 分组。
对比技能类型基线、语义适用门控与收益门控；状态标签不能直接由整条任务输赢替代。
最终验证需要另外封存、且未参与规则选择的场景或任务集。
